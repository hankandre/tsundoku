# Bun + Hono Backend Rewrite Plan (Big-Bang, 100% API Parity)

## Scope and Goals
- Replace the current Java/Spring backend in `booklore-api` with a Bun runtime + Hono.js backend.
- Keep API behavior fully compatible for first release: same routes, auth behavior, status codes, payload shapes, and error contract.
- Perform a big-bang cutover (single switchover), with parity validated before release.
- Use Drizzle as the Bun data access layer.
- Target PostgreSQL as the runtime database for better operational safety than file-based DBs.

## Key Existing Backend Areas to Mirror
- App entry + runtime config: `booklore-api/src/main/java/org/booklore/BookloreApplication.java`, `booklore-api/src/main/resources/application.yaml`.
- HTTP/API controllers: `booklore-api/src/main/java/org/booklore/controller/*Controller.java`.
- Security/auth stack (JWT, basic auth, route-specific filters, OIDC): `booklore-api/src/main/java/org/booklore/config/security/SecurityConfig.java`, `booklore-api/src/main/java/org/booklore/config/security/**/*`.
- Global error contract: `booklore-api/src/main/java/org/booklore/exception/GlobalExceptionHandler.java`.
- Data layer + schema: `booklore-api/src/main/java/org/booklore/model/entity/**/*`, `booklore-api/src/main/java/org/booklore/repository/**/*`, `booklore-api/src/main/resources/db/migration/*.sql`.
- Background jobs/tasks: `booklore-api/src/main/java/org/booklore/service/task/*`, `booklore-api/src/main/java/org/booklore/task/**/*`, `booklore-api/src/main/java/org/booklore/crons/*`.
- WebSocket/STOMP behavior: `booklore-api/src/main/java/org/booklore/config/WebSocketConfig.java`.

## Recommended Migration Approach
1. Build a parallel Bun+Hono backend implementation in a new folder (keep Java backend untouched until parity passes), using `booklore-api-bun/`.
2. Freeze API contract from the current Java backend using generated route matrix + golden request/response fixtures.
3. Implement Hono route groups by domain, but defer cutover until all parity checks pass.
4. Introduce Bun workspaces to make the repo a monorepo and wire both UI/backend tooling through workspace scripts.
5. Switch compose, Docker, and CI to Bun backend after parity suite is green.

## Implementation Steps

### 0) Dependency Research and Lock-In (Latest Stable First)
- Before coding, establish a dependency baseline doc for `booklore-api-bun` with package purpose, selected version, and replacement policy.
- Use official release sources (npm + GitHub releases) and prefer latest stable (not canary/beta) unless a specific bugfix requires otherwise.
- Initial recommended stack (to verify at implementation start):
  - Runtime/tooling: `bun` (latest stable; currently 1.3.x from Bun blog releases).
  - HTTP framework: `hono` (latest stable; currently 4.12.x).
  - Node adapter/helpers when needed by integration points: `@hono/node-server`, `@hono/node-ws`.
  - Validation + OpenAPI: `zod` (4.x), `@hono/zod-openapi` (1.x).
  - DB: `drizzle-orm` (latest stable), `drizzle-kit` (latest stable), `postgres` (postgres.js 3.x) as primary driver.
  - Auth/JWT/OIDC crypto: `jose` (6.x).
  - Logging: `pino` (10.x), with optional pretty transport for dev only.
  - Testing: `vitest` (4.x) and HTTP contract test helpers.
- Security default: use Bun-native `Bun.password` (Argon2id default) for password hashing to minimize external crypto dependencies.
- Phase-1 dependency posture: minimal-deps-first; prefer Bun/Hono built-ins before adding new third-party packages.
- Add explicit dependency update policy:
  - Pin exact versions for runtime-critical packages in first release.
  - Schedule post-cutover upgrades in small batches with parity suite reruns.

### 0.5) Deep API/Docs Research Stage (via `deep_researcher_start`)
- Run a focused research pass before implementation using `deep_researcher_start` + `deep_researcher_check` for each core technology:
  - Bun runtime APIs (HTTP/server behavior, `Bun.password`, WebSocket/runtime caveats)
  - Hono routing/middleware patterns and Bun deployment specifics
  - Drizzle ORM + Drizzle Kit (PostgreSQL schema/migrations/transactions)
  - PostgreSQL driver patterns (`postgres`), pooling and connection lifecycle
  - `jose` JWT/OIDC primitives and best-practice token validation flows
  - `zod` + `@hono/zod-openapi` request/response validation and OpenAPI generation
  - `vitest` patterns for HTTP contract and integration testing under Bun
- For each researched area, capture:
  - Latest stable version guidance
  - Recommended patterns to adopt
  - Known pitfalls/edge cases and mitigations
  - Migration notes relevant to Java/Spring parity
- Save outputs as implementation references in `booklore-api-bun/docs/research/` (one markdown file per technology) and maintain a short consolidated decision record in `booklore-api-bun/docs/dependencies.md`.

### 1) Contract Freeze and Inventory
- Generate authoritative endpoint inventory from controllers in `booklore-api/src/main/java/org/booklore/controller/*Controller.java` (method, full path, auth type, params, status codes).
- Capture real responses from the Java backend for representative success/error cases per route family (golden fixtures).
- Map cross-cutting contracts:
  - Auth modes: JWT, OPDS/Komga basic auth, KOReader/Kobo flows, media token flows.
  - Validation/error shape from `GlobalExceptionHandler`.
  - Pagination/sorting/filter conventions.

### 2) Scaffold Bun + Hono Project
- Create `booklore-api-bun/` with Bun + TypeScript + Hono.
- Add root Bun workspace config so `booklore-api-bun` and existing packages can be managed from the monorepo root.
- Proposed structure:
  - `booklore-api-bun/src/index.ts` (server bootstrap)
  - `booklore-api-bun/src/app.ts` (Hono app composition)
  - `booklore-api-bun/src/config/*` (env/config parity with `application.yaml`)
  - `booklore-api-bun/src/middleware/*` (auth, CORS, logging, error mapping)
  - `booklore-api-bun/src/routes/**` (controller parity by domain)
  - `booklore-api-bun/src/services/**` (business logic)
  - `booklore-api-bun/src/db/**` (Drizzle + PostgreSQL access, migrations wiring)
  - `booklore-api-bun/src/tasks/**` (scheduled/background jobs)
  - `booklore-api-bun/src/ws/**` (WebSocket support)
  - `booklore-api-bun/docs/dependencies.md` (dependency decisions + version rationale)

### 3) Data and Persistence Parity (Drizzle + PostgreSQL)

**Phase A - Immediate (Current):**
- Use raw SQL via `postgres` driver for quick iteration
- Direct SQL queries in services (e.g., `src/services/user-service.ts`)
- Establish schema parity with legacy MariaDB migrations

**Phase B - Mid-term (Post-UUID migration):**
- Migrate raw SQL to Drizzle ORM
- Create Drizzle schema files in `src/db/schema/`
- Generate migrations via `drizzle-kit`
- Replace manual SQL with type-safe Drizzle queries

- Treat current MariaDB/Flyway schema as legacy source in `booklore-api/src/main/resources/db/migration/*.sql`.
- Create a Drizzle schema + PostgreSQL migration baseline in the new Bun backend (`booklore-api-bun/src/db/schema/*`, `booklore-api-bun/drizzle/*`).
- Implement repository-equivalent query modules with Drizzle for existing entity/repository behavior.
- Add explicit transaction boundaries for multi-write operations currently handled via Spring/JPA.
- Fresh-install strategy for first release (no MariaDB -> PostgreSQL migration tooling in phase 1).

### 4) Security and Session/Auth Parity
- Recreate route-level auth matrix currently encoded in `SecurityConfig.java`:
  - Public endpoints (`/api/v1/auth/**`, `/api/v1/setup/**`, `/api/v1/public-settings`, `/api/v1/healthcheck/**`, etc.).
  - OPDS/Komga basic auth segments.
  - JWT-protected API segments and token-query media routes.
  - KOReader/Kobo specific auth flows.
  - OIDC callback/session/logout flows.
- Preserve CORS behavior and defaults from `application.yaml`/`SecurityConfig`.

### 5) Route-by-Route Domain Implementation
- Port routes domain-wise from `controller/*Controller.java` into matching Hono route modules.
- Prioritize high-risk/complex groups first:
  - Auth/user/session/permissions
  - Book/media/file streaming/upload
  - Kobo/KOReader/OPDS/Komga integrations
  - Metadata/task/cron orchestration
- Ensure response envelope and status code parity for all known error cases.

### 6) Background Tasks and Scheduling
- Rebuild task execution, cancellation, history, and cron config behavior from:
  - `service/task/TaskService.java`
  - `service/task/TaskHistoryService.java`
  - `service/task/TaskCronService.java`
  - `task/tasks/*.java`
- Reproduce periodic jobs and operational semantics in Bun scheduler workers.

### 7) WebSocket/Eventing Parity
- Mirror `/ws` endpoint behavior and auth gating from `WebSocketConfig.java` and related interceptors.
- Preserve topic naming and payload conventions used by the frontend.

### 8) Build, Container, and CI Cutover
- Update runtime/build pipeline files to Bun backend:
  - `dev.docker-compose.yml`
  - `Dockerfile`
  - `Dockerfile.ci`
  - `entrypoint.sh` (if still needed)
  - `.github/workflows/develop-pipeline.yml`
  - `.github/workflows/master-pipeline.yml`
  - `.github/workflows/migrations-check.yml` (if migration mechanism changes)
- Replace Gradle backend test/build commands with Bun equivalents while preserving artifact and report publishing in CI.
- Configure DB connectivity via environment variable URI (e.g. `DATABASE_URL`) so deployments work with self-hosted Postgres or PaaS Postgres.
- Keep local/dev compose support optional, but do not hard-couple runtime to an in-stack DB service.

## Risk Areas and Mitigations
- Security drift: encode and test full route-auth matrix with automated auth regression tests.
- ORM/transaction differences: begin with explicit SQL/transaction wrappers for critical flows before optimization.
- Fresh-install-only release risk: communicate clearly in docs/release notes that existing MariaDB deployments are not auto-migrated in phase 1.
- Streaming/media behavior mismatches: add byte-range, headers, and cache behavior contract tests.
- Integration protocol regressions (Kobo/KOReader/OPDS): add protocol-specific golden tests before cutover.
- Background job semantics changes: add deterministic tests around scheduling/cancellation and idempotency.

## Verification Plan (End-to-End)
1. Baseline current Java backend
- Run existing backend tests in `booklore-api` and store results.
- Generate API endpoint matrix + golden fixtures from running Java service.

2. Validate Bun backend locally
- Start PostgreSQL + Bun backend in Docker/compose.
- Run Bun unit/integration tests.
- Run parity suite comparing Bun responses against golden Java fixtures (status, headers, payload, error shape).

3. Frontend compatibility check
- Start `booklore-ui` against Bun backend and run frontend tests.
- Execute smoke flows: login, library browsing, reading/progress sync, metadata tasks, media streaming.

4. Pre-cutover gate
- Require: 100% parity suite pass, critical integration pass (Kobo/KOReader/OPDS), no regression in CI pipeline.

5. Big-bang release validation
- Deploy Bun image to staging with production-like data.
- Run post-deploy smoke and protocol checks.
- Cut over production traffic once staging signoff is complete.
