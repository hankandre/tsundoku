# Plan: Flush Unimplemented `tsundoku-api` Routes

## Goal
Implement unimplemented routes using a **core reading flow first** strategy: prioritize endpoints required for reading, downloading, browsing by library/shelf, and tracking progress.

## Scope
- In scope: `apps/tsundoku-api` only.
- Out of scope for now: advanced/admin-heavy metadata tooling and recommendation/duplicate logic.

## TDD Execution Model (Required)

For each capability slice, use a strict two-agent workflow:

1. **Test Agent (integration-first)**
   - Writes integration tests for the target routes first.
   - Confirms tests fail for the expected reason (placeholder behavior).
   - Produces a concise handoff report: test files, assertions covered, current failure output.

2. **Implementation Agent (red -> green)**
   - Implements route/service behavior to satisfy existing tests.
   - **Hard rule:** does not modify test intent to match business logic shortcuts.
   - Allowed test edits are limited to fixing objectively broken tests (typos, invalid fixtures), and must be explicitly documented in handoff.

3. **Guardrail**
   - If implementation is blocked by ambiguous requirements, stop and request clarification instead of weakening assertions.
   - Prefer extending services over embedding complex logic in route handlers.

## PR / Delivery Strategy
- Keep PRs small and vertical (tests first, then implementation for one capability).
- Recommended order:
  1. book file serving + OPDS download
  2. shelf/library browse endpoints
  3. reading progress/status/rating
  4. shelf assignment + viewer settings
  5. remaining secondary endpoints
- Suggested PR shape per slice:
  - PR A: integration tests only (failing expected)
  - PR B: implementation to make PR A tests pass

## Verification Plan

### Automated
- Red phase:
  - run only new route integration tests and confirm expected failures.
- Green phase:
  - rerun targeted tests until passing.
- Regression phase:
  - `bun --filter tsundoku-api test`
  - For targeted runs, use file-specific test commands in `tsundoku-api` package scripts.

### Manual API checks (per implemented route)
- Validate auth/authorization behavior (401/403 paths).
- Validate not-found behavior (404 paths).
- Validate success payload shape matches existing conventions.
- For download/content routes, verify headers:
  - `Content-Type`
  - `Content-Disposition` (download)
  - Range/stream behavior where applicable.

### End-to-end smoke
- Start API and exercise:
  - library -> shelf -> book detail -> content/download -> update progress/status.
  - OPDS root -> library feed -> acquisition download.

## Definition of Done
- Route no longer returns placeholder `501`/stub `404` for in-scope endpoint.
- Validation, authorization, and error semantics are consistent with existing route patterns.
- Service logic lives outside handlers and remains readable/low complexity.
- Integration tests were authored first and preserved in intent.
- Tests added/updated and passing for changed behavior.
